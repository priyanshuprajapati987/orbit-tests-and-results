# Patch: Stub/Fake Security Responses Without Warning

**Date:** 2026-08-23
**Severity:** CRITICAL
**Tags:** #python #security #stubs #misleading
**Files:** incident_actions.py, device_manager.py

## Problem
`rotate_all_api_keys()` returned `{"status": "keys_rotated", "count": 5}` — a fake success response. The function was a stub that did nothing. Similarly, `device_manager.invalidate_sessions()` iterated over an empty dict `_get_sessions() → {}`, so it never actually invalidated anything.

These fake responses were indistinguishable from real success — security audits and incident response would pass while nothing actually happened.

## Root Cause
Functions were stubbed during development with fake success responses instead of proper stub markers. No warning was logged, no status区分 between real and stub.

## Prevention
- **aif-implement:** When creating a stub function, ALWAYS: (1) return `{"status": "stub", "action": "name", "message": "not yet implemented"}`, (2) log a WARNING level message, (3) never return fake success codes. Use this exact pattern:
  ```python
  def stub_action():
      log.warning("action_name: NOT IMPLEMENTED — returning stub")
      return {"status": "stub", "action": "action_name", "message": "not yet implemented"}
  ```
- **aif-review:** Check security-related functions for stub patterns. Look for functions that return success without actually performing the action.
- **aif-fix:** When finding fake security responses, replace with proper stub markers AND add logging.

## Evidence
- Commit `2e0caee` — replaced fake `rotate_all_api_keys` with stub marker + warning; fixed `device_manager._get_sessions()` to return real session data
